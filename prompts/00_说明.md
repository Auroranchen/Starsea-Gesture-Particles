**核对状态**：原始对话已从实际使用的 AI 工具导出（见 [`original/`](original/)），并与复盘逐项核对；两者如有出入，以原始记录为准。赛道提交规则须以官方文件为准。

`传智杯要求.docx` 是二次汇总，不等于官方原文。复盘可解释技术取舍；原始对话才可证明当时确实如此提问、回复与修正。

### 2. 每篇的结构

统一为五段，对应评分点「方法创新性与意图控制」：

| 段落 | 回答的问题 | 对应评分点 |

| ① 迭代目标 | 这次要做成什么样 | 痛点定义 |

## 我在这场协作中养成的 7 条习惯

以下七条为技术复盘总结，具体轮次以 [`original/`](original/) 的原始记录为准：

1. **先给约束，再给需求。** 第一句话永远是"不许改哪些东西"，比如"不要动
   `nebula`/`galaxy`/`ocean` 的现有表现，只新增一个场景"。不设边界，AI 一定会顺手重构你
   没让它碰的地方。

2. **一次只让它改一个文件。** 着色器、TS 逻辑、UI 分三轮提，不要一句"把土星加上"。
   混着改的时候，出了错你无法定位是哪层的问题。

3. **要求它先解释再动手。** "先说清楚你打算怎么在倾斜环面里分解受力，等我确认再写"——
   这一步能挡掉大约一半的错误方向，成本只有几十秒。

4. **给出可计算的判据。** 例如土星环的目标线速度可按 `v ∝ r^-0.5` 建模，对应角速度 `ω ∝ r^-1.5`；具体内外环速度比需给定半径计算。此处是技术分析示例，不能冒充当时的原始提问。

5. **让它复述改动清单。** 每轮结束要求"列出你改了哪几行、为什么"。这既是我的 review
   清单，也逼它自查有没有越界。

6. **物理量一律进 `config.ts`。** 任何硬编码在着色器里的魔数都是未来的债。我把这条
   变成硬约束后，调参效率提高了一个数量级，也让"AI 生成的代码"变得可被人接管。

7. **先给规范，再给需求；只给适用的部分。** 动手写 UI 之前，我先把一套**与框架无关**的
   设计约定灌进上下文——间距尺度、状态归属的判断标准、文案语气、错误提示的写法。
   目的是让一个月后追加的代码和今天的代码看起来出自同一个人。
   但绝不整包投喂：那套规范里有一半是为 React 写的（属性命名、组件组合、hooks 依赖），
   而本项目 UI 层是原生 TypeScript + 直接 DOM 操作，没有组件树也没有 hooks。
   全量喂进去，AI 会照着并不存在的概念搭出一堆空包装。**给错了上下文比不给更糟。**
