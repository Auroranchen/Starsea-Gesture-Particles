# AI 协同开发 · Prompt 历史快照

本目录是「智控星海」项目在 AI 辅助开发过程中保存的 **Prompt 迭代记录**，对应赛题
"至少 3 个核心功能迭代的完整 Prompt 链"要求。

---

## 📌 关于本目录的两点必读说明

### 1. 文件性质

本目录中的 3 篇记录，是根据**代码中的真实痕迹**（commit、代码注释里记录的技术决策与踩坑、
`config.ts` 中逐个参数背后的调参过程）**回溯整理**的完整 Prompt 链。

**提交前请务必做一件事**：把你使用的 AI 工具（Cursor / Windsurf / Trae / 通义灵码 /
DeepSeek / ChatGPT 等）里对应的**原始对话截图或导出文件**，与本文档并列放进本目录，
命名如 `01-原始对话截图-01.png`。

理由：赛题原文要求"使用 AI 工具需要导出和 AI 的对话历史，如果 AI 工具不支持导出，
可以截图或者录屏"。整理稿说明了"为什么这么改"，原始导出证明了"确实这么问过"，
两者互补才构成完整证据链。只有整理稿而没有原始导出，说服力会打折。

### 2. 每篇的结构

统一为五段，对应评分点「方法创新性与意图控制」：

| 段落 | 回答的问题 | 对应评分点 |
|---|---|---|
| ① 迭代目标 | 这次要做成什么样 | 痛点定义 |
| ② 上下文投喂 | 我给 AI 看了什么、没给它看什么 | 上下文管理 |
| ③ Prompt 链 | 每一轮的提问 + AI 的回应要点 + 我的判断 | 意图控制 |
| ④ 踩坑与修正 | 哪一轮跑偏了、怎么拉回来 | 引导修复 Bug 的能力 |
| ⑤ 落地证据 | 改了哪些文件、对应哪个 commit | 可复现性 |

## 我在这场协作中养成的 7 条习惯

这些不是事后总结的漂亮话，而是每次迭代都在用的具体做法：

1. **先给约束，再给需求。** 第一句话永远是"不许改哪些东西"，比如"不要动
   `nebula`/`galaxy`/`ocean` 的现有表现，只新增一个场景"。不设边界，AI 一定会顺手重构你
   没让它碰的地方。

2. **一次只让它改一个文件。** 着色器、TS 逻辑、UI 分三轮提，不要一句"把土星加上"。
   混着改的时候，出了错你无法定位是哪层的问题。

3. **要求它先解释再动手。** "先说清楚你打算怎么在倾斜环面里分解受力，等我确认再写"——
   这一步能挡掉大约一半的错误方向，成本只有几十秒。

4. **给它可验证的判据。** 不说"看起来要真实"，而说"环内缘角速度必须大于外缘，比值约
   1.5；环面倾角 0.42 rad 时环不能出现上下翻涌"。模糊目标会得到模糊代码。

5. **让它复述改动清单。** 每轮结束要求"列出你改了哪几行、为什么"。这既是我的 review
   清单，也逼它自查有没有越界。

6. **物理量一律进 `config.ts`。** 任何硬编码在着色器里的魔数都是未来的债。我把这条
   变成硬约束后，调参效率提高了一个数量级，也让"AI 生成的代码"变得可被人接管。

7. **先给规范，再给需求；只给适用的部分。** 动手写 UI 之前，我先把一套**与框架无关**的
   设计约定灌进上下文——间距尺度、状态归属的判断标准、文案语气、错误提示的写法。
   目的是让一个月后追加的代码和今天的代码看起来出自同一个人。
   但绝不整包投喂：那套规范里有一半是为 React 写的（属性命名、组件组合、hooks 依赖），
   而本项目 UI 层是原生 TypeScript + 直接 DOM 操作，没有组件树也没有 hooks。
   全量喂进去，AI 会照着并不存在的概念搭出一堆空包装。**给错了上下文比不给更糟。**
