# AI 协作案例：三次「AI 给了方案，我没照单全收」

> **素材来源**：`prompts/original/04_Bug修复与验证.md`（原始会话导出，未改写），
> 对应 `prompts/original/raw/6e680cf0-*.jsonl` 与 `e7fd70cf-*.jsonl`。
> 文中 Prompt 与 AI 回复均为**原文引用**；属于我事后归纳的部分单独标注「复盘」。
> 凡无法从原始记录核实的，一律写「无法核实」，不补写情节。

写这份文件的目的不是展示 AI 有多能干——恰恰相反，是展示**它出错时我怎么发现、怎么纠正、以及把教训固化成了什么机制**。赛题评分表里 20% 的「对 AI 智能体的驾驭能力」，落在纸面上就是这三件事。

---

## 案例一：AI 越界改动 + 着色器静默失败（影响面最大的一次）

### 背景

2026-10-19，我让它只优化 `nebula` 和 `ocean` 两个场景的特效。

### 我当时的 Prompt（原文）

```text
nebula和ocean的特效有点一般，你升级一下，必要时可以参考一下github上面的特效，以我的主题色为主
```

### AI 做了什么

它改了 6 个文件（`config.ts`、`ParticleSystem.ts`、`StateMachine.ts`、`velocity.frag.glsl`、`points.vert.glsl`、`points.frag.glsl`），并在回复末尾给出验证结果——**其中最关键的一句是**：

```text
- `npm run build` 已通过。
- TypeScript 编译和 Vite 构建均成功。
- 浏览器自动检查未能执行，因为当前环境没有 `chromium-cli`。
```

也就是说：**它用「构建通过」代替了「效果正常」，并明确知道我无法在浏览器里验证。**

### 我的判断（原文）

```text
我单纯让你优化nebula和ocean的特效，你怎么把galaxy和saturn的也改了，特效都没了
```

### AI 的承认（原文）

```text
查到一个明确的问题：我在 `points.frag.glsl` 里新增了 `vCrest`，但没有在对应的片元 shader 中声明它。
这会导致 GPU 粒子材质的着色器编译失败，影响所有场景，而不只是 nebula 和 ocean。
我已经补上声明，并重新运行 `npm run build`，构建通过。

但**构建通过不等于确认 galaxy 和 saturn 已恢复**：当前环境没有可用的浏览器检查工具……
抱歉之前把代码分支未改误当成了视觉效果不受影响。
```

### 复盘：这次真正暴露的三个问题

1. **越界**：要求只动 A、B，实际改了共享着色器，波及 C、D；
2. **静默失败**：`varying` 用了没声明，**构建不报错**，只在运行时让整条着色器编译失败——表现是所有场景的粒子一起消失；
3. **验证标准错位**：把「能构建」当成了「能运行」。

### 沉淀成了什么机制（这三条现在都在仓库里）

| 机制 | 位置 | 怎么防住同类问题 |
|---|---|---|
| 运行期错误可视化 | `src/main.ts` 的 `installErrorReporter()` | 把 `window.onerror`、`unhandledrejection`、`console.error` 直接画到页面底部，黑屏有线索 |
| 视觉参数铁律 | `AGENTS.md` | 明确「`.glsl` 的视觉参数与调色板不动产」，改之前必须先说明理由 |
| 契约检查脚本 | `scripts/check-contract.mjs` | 检查 uniform 与 varying 的声明一致性，**接入 CI** |

> 说明：`check-contract.mjs` 最初的版本只查 uniform，注释里还写着「历史上虽未发生过命名不一致」——这句话是错的，本文记录的这次事故就是。所以本轮把它扩到了 varying 检查，并把注释改正。**一个检查脚本只覆盖一半的问题，比没有更危险**，因为它会让人误以为查过了。

## 案例二：新交互与旧力场打架

### 我当时的 Prompt（原文）

```text
好的，请你基于另外2个特效不变的情况下，继续优化nebula和ocean，加一点波动，比如说的nebula的特效在检测到我双手握拳时这些分散的星海能汇聚成一个大的行星或者星星。ocean的特效呢，当检测到我双手握拳时平静的星海立刻波动起来
```

### AI 指出的冲突（原文节选）

```text
输入层已经提供左右手各自的握拳判定，可以只在 nebula 和 ocean 中使用"双拳同时成立"来触发效果。
还需要处理现有双手引力和碰撞的叠加，避免星云聚成球后又被手部力场拉散。
```

```text
现在将 B-key fist signal 通过 MouseInput 接入 GestureFrame
```

### 我的判断

它主动指出了我没想到的一件事：**「双手握拳聚拢」和「双手作为碰撞球排斥粒子」这两个力会互相抵消**——球刚聚起来就被手掌推开，形态立不住。这是需求没写清楚时 AI 反而补上的洞，值得采纳。

它顺带加了一个「鼠标按住 `B` 键模拟双拳」的入口。我最初以为这是开发期的临时便利，打算交付前砍掉，理由是「课堂上不会有人一边按 B 一边演示」。

**这个判断是错的。** 当时我只扫了 `MouseInput.ts` 里的 `e.key ===` 判断，没看 `e.code ===`，就得出「代码里没有 B」的结论，还在本文档初版里写成了既成事实。实际上 `B` 一直在：

```ts
// src/input/MouseInput.ts:124 / :131
if (e.code === 'KeyB') this.fistDown = true;    // 按下
if (e.code === 'KeyB') this.fistDown = false;   // 松开
// :173
bothFists: this.fistDown ? 1 : 0,
```

而且它不砍是对的：nebula 聚成大行星、ocean 起浪这两个形态**只在双手都握拳时出现**，没有摄像头的人（比如在自己电脑上试用的评委）如果连 `B` 都没有，就永远看不到这两段效果。它不是开发便利，是**无摄像头场景下的必要兜底**。

> 这条的教训不是「AI 提的建议该采纳还是该砍」，而是**我对自己代码的判断也不能凭印象**。写这句结论之前只要 grep 一次 `KeyB` 就能发现，我没做。

## 案例三：需求含糊时，它先核对再动手

### 我当时的 Prompt（原文）

```text
把我"D:\桌面软件\传智杯\最终结果"里面nebula和ocean的特效改回原来的，其他不变
```

### AI 的处理（原文节选）

```text
已定位到可对照的原始三场景版本。nebula/ocean 的动力学参数和力场本身没有被改动，
实际差异主要在 nebula 配色、ocean 按钮强调色，以及新版粒子片元着色器把额外的闪烁/形状/深度效果也套到了这两个场景上。

我查了相邻的三场景原始项目：nebula 和 ocean 的核心模拟参数、状态更新和力场公式在「最终结果」里仍与原版一致；
变化集中在 nebula 的配色和 ocean 的强调色。因此目前没有改动文件。
```

### 我的判断

它没有直接执行「改回」，而是先对照了两份代码，得出「动力学没变、差异在配色」的结论，**并停在了没动文件的状态**——这个处理是对的。如果我当时强行让它「改回去」，它会去还原一堆本来就没被改过的参数，反而制造新的偏差。

这次之后我改了问法：不再说「改回原来的」，而是直接说清想要的效果（见案例二的 Prompt）。

## 这三件事的共性

三次都不是「AI 写不出代码」，而是：

1. **验收标准由谁定**——AI 默认用「构建通过」，我必须把标准拉到「浏览器里看得见」；
2. **改动边界由谁守**——AI 会顺着「优化特效」一路改到共享着色器，边界得我划；
3. **AI 的自我报告不可全信**，但**它指出的技术冲突通常是真的**。

对应到流程上就是三样东西：`AGENTS.md`（划边界）、`check-contract.mjs`（机器验收）、运行期错误可视化（人眼验收兜底）。
